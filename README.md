# all-in-one — три сервиса в одном контейнере

Склейка `gamepass-backend` + `vibecod-relay` + `tg-transcriber-bot` в один
образ, чтобы уместиться в бесплатный тариф Render.

`planerdenbot` в склейку не входит — погашен 10.08.2026, см. раздел о памяти.

## Зачем

Бесплатный Render даёт **750 инстанс-часов в месяц на весь воркспейс**, а не на
сервис. Один всегда-включённый сервис съедает ~744 часа в 31-дневном месяце —
влезает. Два съедают ~1488 и вешают суспенд на весь аккаунт в середине месяца.
Именно так мы и слегли 28 июня 2026, после чего уехали на Fly.

Отсюда правило: **на бесплатном Render у нас может быть ровно один сервис.**
Любой новый бот добавляется процессом внутрь этого контейнера, а не рядом.

## Устройство

```
                    один публичный порт ($PORT)
                              │
                          ┌───▼───┐
                          │ nginx │  роутер по префиксам
                          └───┬───┘
        ┌──────────────┬──────┴───────┐
        │              │              │
   /api/, /socket.io/  /relay/   /transcriber/
        │              │              │
   gamepass:3001   relay:8081  transcriber:8082
     Node             Python       Python
```

Всё держит `supervisord`: каждый процесс перезапускается сам, падение одного
бота не роняет игры. `/health` отвечает сам nginx — иначе перезапуск одного
сервиса уронил бы health-check и хостинг убил бы весь контейнер целиком.

## Развязка токенов

В отдельных приложениях у каждого был свой `BOT_TOKEN`. В одном контейнере
окружение общее, и имена сталкиваются:

| Переменная | Кто спорит |
|---|---|
| `BOT_TOKEN` | gamepass (`@Liquid_Chess_bot`) и relay (`@Myvibecodbot`) |

Решено без правки исходников: снаружи задаются префиксные имена
(`GAMEPASS_BOT_TOKEN`, `RELAY_BOT_TOKEN`, `TRANSCRIBER_BOT_TOKEN`), а `supervisord.conf` раздаёт каждому процессу то
непрефиксное имя, которое его код уже читает.

## Что придётся переключить при запуске

Адреса меняются у всех трёх.

1. **Вебхук геймпаса** → `https://<host>/api/telegram/webhook`
2. **Вебхук самаризатора** — регистрируется сам из `WEBHOOK_BASE_URL`, задать
   `https://<host>/transcriber`
3. **Вебхук `@Myvibecodbot`** → `https://<host>/relay/webhook/<секрет>`
4. **`RELAY_URL` в `apps/tg-mac-agent/.env` на Маке** → `https://<host>/relay`.
   Без этого Мак продолжит стучаться на Fly и агент отвалится.
5. **`frontend/.env.production`** в репозитории GamePass — `VITE_API_URL` и
   `VITE_WS_URL` на новый хост, затем передеплой Vercel.

## Нерешённое: диск

На бесплатном Render **нет постоянного диска**, `/data` стирается при каждом
деплое. Состояние там держат двое:

- **relay** (`RELAY_DB`) — очередь команд и снимки сессий. Живут секунды,
  потерять не жалко.
- **самаризатор** (`STATE_DB_PATH`) — пользовательская память и напоминания.
  Вот это терять нельзя, иначе мы воспроизведём ровно тот баг со слетающими
  данными, ради починки которого и переезжали на Neon.

**Перед боевым запуском состояние самаризатора надо перенести в Neon.**
База там уже есть (тот же Neon, что у геймпаса), в бесплатном гигабайте
места хватает.

## Ограничения тарифа

| | Free Render | Сейчас на Fly |
|---|---|---|
| Память | 512 МБ на всё | 1.5 ГБ суммарно |
| CPU | 0.1 ядра на всё | по shared-ядру каждому |
| Диск | нет | тома у relay и самаризатора |
| Трафик | 5 ГБ/мес | 100 ГБ |

0.1 CPU — самое узкое место и единственное непроверенное. Node с socket.io
плюс два Python-процесса на десятой доле ядра будут заметно медленнее, чем
сейчас; замера под нагрузкой ещё не было.

## Замер памяти (10.08.2026, arm64)

Собрано и измерено. Установившийся `VmRSS`, простой, без нагрузки:

| Компонент | Память |
|---|---:|
| nginx | ~10 МБ |
| supervisord | ~18 МБ |
| relay (aiohttp) | 34 МБ |
| transcriber (реальный набор импортов старта) | 157 МБ |
| gamepass (Node + Prisma), без живой базы | 55 МБ |
| **итого в простое** | **~274 МБ** |

С живым Neon у геймпаса поднимется Prisma query engine — реалистично 150 МБ
вместо 55, тогда сумма ~369 МБ. **Против потолка Render в 512 МБ запас ~143 МБ.
По памяти влезаем.**

Планер (`planerdenbot`) в расчёте отсутствует: погашен 10.08.2026
(`fly scale count 0`), именно он ломал бюджет.

### Почему aiogram решает всё

`aiogram` стоит **145 МБ сама по себе** — при импорте она строит сотни моделей
Telegram API. Для сравнения: `pydantic` из них всего 8 МБ, `groq` добавляет 4,
`dotenv` и `aiohttp` вместе 1.6.

Отсюда правило: **каждый aiogram-бот отдельным процессом стоит ~145 МБ,
и эта память не делится между процессами.** Два бота = 290 МБ, больше половины
бесплатного тарифа. Именно поэтому планер и самаризатор вместе не помещались.
Если понадобится второй бот — держать его в том же процессе (aiogram умеет
несколько `Bot` и `Dispatcher` в одном), а не рядом.

### Чистить самаризатор нечего

Проверено: все тяжёлые зависимости **уже импортируются лениво**, внутри
функций — `anthropic` (строки 861, 1193, 1538), `pypdf` (1277, 4455),
`yt_dlp` (3780), `reportlab` (4085+), `PIL`/`pillow_heif` (4247+),
`img2pdf` (4286). На старте грузятся только `aiogram`, `groq`, `dotenv`,
`aiohttp`. Собственный код бота и все его функции — меньше 13 МБ.

Единственный способ ужать самаризатор — уйти с aiogram на голые вызовы Bot API
через aiohttp. Это переписывание `bot.py` на 226 КБ, ради ~145 МБ. Не стоит
того, пока мы помещаемся.

Замер сделан на arm64, Render работает на amd64 — цифры могут немного
отличаться, но не в разы.

### Повторить замер

```bash
docker build -t allinone:test .
docker run -d --name mtest -m 512m --memory-swap 512m --env-file .env.local allinone:test
docker stats --no-stream mtest
```

`-m 512m` обязателен — он воспроизводит потолок Render.
